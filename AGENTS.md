# Analytics Lab development instructions

## Mission and scope
Develop original analytics for paid distribution inside the owner's platforms. This is an independent source-available commercial R&D repository, not a free-use product or a fork of the VMS. Preserve LICENSE and all upstream notices. Do not modify other repositories, production deployments, camera settings, home-camera access, self-hosted runners, or other agents' schedules.

The owner delegates routine research, implementation, testing, and narrow validated Analytics-lab merges. No spending, external contracts, licensing changes, physical actuation, or production/commercial release is delegated. An IP/software attorney should review commercial legal terms before release; engineering provenance checks are not a legal opinion.

## Execution loop
Read live main, this file, docs/PROJECT_STATE.md, ops/efficiency-policy.json, open PRs, and actual CI. Continue one implementation PR at a time; never create a competing successor. Fix the first demonstrated failure before scope expansion. Use small concrete code and test increments rather than status-only commits or repeated redesigns. Check head freshness before writing; do not force push. Merge only when the exact current head has verified passing required tests and no unresolved regression. An unrun check is unknown, not passed. Do not lower quality gates to get green.

Notify the owner only for meaningful verified milestones, material regressions, or decisions requiring owner access, licensing authority, spending, hardware or commercial-release approval. Do not ask the owner to manage ordinary implementation. A scheduled invocation is bounded work, not a continuously running developer or a guarantee of delivery.

## Efficiency guardrails
The limits in ops/efficiency-policy.json are ceilings, not activity targets. Keep ONE worker, ONE acceptance-moving work item and at most ONE implementation PR. Do not create extra auditor/planner agents, competing implementations, status-only branches or elaborate reporting systems. After this control setup, return to the next product boundary; do not repeatedly polish governance instead of shipping tested functionality.

Before a mutation or CI request, verify live repository/head/base, open PRs and relevant queued/running/completed checks. Build a local snapshot and run `python tools/guardrails.py preflight --snapshot <local-json-path>`. The snapshot must contain repository, live_state_verified=true, action (implement/dispatch_ci/retry_ci/research), open_implementation_prs, active_runs_for_head, unchanged_ci_retries, ci_dispatches_this_session, and sessions_without_progress. Use actual nonnegative counts, not invented zeros. This checker evaluates supplied facts; it does not authenticate them, grant permissions, or provide a distributed lock. A missing execution tool does not waive the limits: record the blocker and do not claim a machine check ran.

Reuse the active branch. Before opening a PR, count the proposed PR toward the WIP limit. A queued/running current head blocks duplicate dispatch and mutation; narrow read-only research or local diagnosis for the same work item may continue. Batch a coherent tested change into one push. Do not push to invalidate a healthy run. Main post-merge verification is intentional, not a duplicate feature-branch run.

Allow at most ONE unchanged retry, and only for a diagnosed transient infrastructure fault. Deterministic failures require a fix before retry. Allow at most TWO CI-triggering pushes/dispatches/retries per session; the verified merge's automatic main run is accounted separately. Exhaustion means diagnose locally, not start a new branch, workflow or agent. Counters follow the work item/head/failure across invocations and cannot be reset by renaming it. Store counters and the last concrete outcome in the existing PR body while work is open; update docs/PROJECT_STATE.md alongside substantive code changes, never merely to trigger CI.

After TWO consecutive sessions without a tested acceptance improvement, shrink the next step or change the failing approach. After THREE, stop that stalled path and record one concrete blocker; use a safe in-scope alternative when possible. Contact the owner only when the remaining action requires owner authority or no safe executable path exists. Keep the scheduled worker enabled; do not pause unrelated work or invent success.

Research at most THREE donor candidates for a missing component, then select the smallest rights-cleared baseline or document the precise missing right/capability. Reuse pinned primary-source evidence unless the artifact or terms changed. Do not re-scan the market, retrain commodity detectors, pull entire donor repositories, or add a second framework without a measured unmet requirement.

Progress means a reproducible capability, a passing regression for a demonstrated bug, a closed integration boundary, or measured cost/failure reduction. Commits, PRs, narration and test count alone are not progress. Record failing and passing tests honestly; synthetic tests do not prove video accuracy. Every benchmark must record source/model/data identities, comparable hardware/settings, positives and negatives, and the baseline delta. First use small deterministic fixtures, then authorized labeled clips, then explicitly bounded robustness runs. No unattended media retention, giant model downloads, GPU jobs, new paid services or benchmark loops without an approved resource/data budget. Cache approved immutable assets; keep private media and bulk intermediates out of GitHub.

Track first-attempt CI failures and runner time per tested outcome, not an unqualified success percentage. For the latest 20 comparable completed runs of a mature workflow, aim for <5% failed first attempts; at >=10%, fix the repeated cause before adding expensive work. Report raw numerator/denominator; fewer than 20 is insufficient trend evidence. Separate expected obsolete-run cancellations and exploratory model failures. Do not rerun to green or weaken assertions to improve metrics. Keep reporting to material outcomes and owner-only decisions.

A verified documentation-only diff skips runtime tests and Windows; unknown history or any code/control change runs full tests. Linux must pass before Windows starts. Superseded PR runs are cancelable; running main verification is preserved. Test jobs have a five-minute ceiling and the final gate a one-minute ceiling.
